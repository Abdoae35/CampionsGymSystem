# Cash Drawer, Shifts, and Member Registration: Manual Postman Guide

This guide is for **you to execute in Postman**. It is based on the current backend source and checked-in Postman collection. No API request, test, or database operation was performed while preparing it. All response values below are **illustrative**; copy the real IDs and amounts from your own responses. Use a testing account and a testing member profile, and verify that port 5236 is connected to your intended testing database before sending a write.

The shortest path through the current backend is:

1. Log in as Sales and copy the employee's branch ID.
2. Log in as Owner, find or create a Cash Financial Account for that branch.
3. As Owner, configure that branch's Shared Drawer with the Cash account and the **actual** cash count.
4. Log in as Sales and open that employee's own Shift.
5. As Sales, register a `NormalSales` Member in the same branch.
6. Retrieve the Member and confirm the Sales assignment.

This order matters. A Cash account is **not** the same thing as a configured Shared Drawer. Member registration checks for the Drawer **before** checking the employee's Shift. [MemberManagementService.Create.cs](../CampionsSystem.BLL/Members/MemberManagementService.Create.cs) · [FinancialOperations.cs](../CampionsSystem.BLL/Shifts/FinancialOperations.cs)

## Before you send anything

In Postman, select the Testing environment. Set `baseUrl` to `http://localhost:5236` **only if that is the API process you have verified is using** `campions_gym_testing`. Source code alone cannot prove which database a currently running process uses.

For protected requests, set **Authorization → Bearer Token** to `{{accessToken}}`. For POST requests, use **Body → raw → JSON** and the header `Content-Type: application/json`. Login is the only request in the main sequence that does not use a bearer token. The controllers normally return HTTP **200** on success. Review the actual body rather than expecting 201. [AuthController.cs](../CampionsSystem.API/Controllers/AuthController.cs) · [BranchControllerBase.cs](../CampionsSystem.API/Controllers/BranchControllerBase.cs)

The collection has both **collection** and **environment** variables. Before each Send, use Postman's variable inspector to see the resolved value. An old environment value can override the collection value. Run one write request at a time; do not run the whole collection as a batch.

| Postman variable | Where its value comes from | When it changes |
|---|---|---|
| `baseUrl` | Your verified Testing API URL, for example `http://localhost:5236` | Only when the server address changes |
| `accessToken` | `POST /api/auth/login` → `accessToken` | Replace it whenever you change between Owner and Sales |
| `branchId` | Sales `GET /api/auth/me` → `currentBranch.id`; users with `Branches.View` can also use `GET /api/branches` | Copy it; do **not** generate it |
| `memberRegistrationBranchId` | For this same-branch exercise, copy `branchId` | Set it to the intended Member registration branch |
| `cashAccountId` | `GET /api/financial-accounts?branchId=...` or account-creation response → `id` of the active `Cash` account | Copy it; do **not** use the InstaPay account ID |
| `drawerCount` | The cash amount you actually counted in the shared physical drawer | Recount before setup and Shift opening; never use the collection's `100000` default blindly |
| `drawerSetupOperationId` | A new UUID generated by you/Postman | One ID for this setup operation; retain it for an exact retry |
| `shiftOpenOperationId` | Another new UUID generated by you/Postman | New ID for each distinct Shift; retain it for an exact retry |
| `shiftId` / `shiftVersion` | `POST /api/shifts` → `id` / `version`, or `GET /api/shifts/current` | Copy the current Shift values; never generate these |
| `memberFullName` / `memberPrimaryPhone` | A new testing Member profile you choose | Use a phone that does not belong to an existing Lead or Member |
| `memberId` | `POST /api/members` → `id` | Copy it for the verification GETs |

**Operation IDs and safe retries.** For a new operation, generate a UUID in Postman using `{{$guid}}` and save its resolved value in the corresponding variable. The collection already has pre-request scripts for drawer setup and Shift opening that create those IDs if the collection variable is empty. If a request times out after you send it, retry with **the same operation ID, same JSON body, and same authenticated user**. A different body or user with the same ID is rejected. A genuinely new setup, count, Shift, or payment needs a new ID. [FinancialOperations.cs](../CampionsSystem.BLL/Shifts/FinancialOperations.cs)

## Step 1 — Identify the Sales employee's branch

### 1A. Log in as Sales

Open Postman folder **`1. Login`**. Send:

| Setting | Value |
|---|---|
| Method and URL | `POST {{baseUrl}}/api/auth/login` |
| Account | Your Sales testing account, for example `test.sales.mohamed` |
| Headers | `Content-Type: application/json`; no bearer token |
| Body | Raw JSON below |
| Permission | Public login endpoint; the account must be usable |

```json
{
  "userNameOrEmail": "test.sales.mohamed",
  "password": "<enter the password locally in Postman>"
}
```

Both fields are required strings with a maximum length of 256. Do not place the password in this file or send it to anyone. A successful response is HTTP 200 with the following **illustrative shape**:

```json
{
  "accessToken": "<JWT returned by the API>",
  "expiresAt": "<UTC timestamp>",
  "user": {
    "id": "<Identity user UUID>",
    "userName": "test.sales.mohamed",
    "employeeId": "<Employee UUID>",
    "fullName": "<employee name>",
    "roles": ["Sales"]
  }
}
```

Copy `accessToken` to the Postman variable of the same name if the collection script has not done so. A 401 response means credentials or account availability must be checked. Next open **`2. Current user`**. [AuthController.cs](../CampionsSystem.API/Controllers/AuthController.cs) · [AuthContracts.cs](../CampionsSystem.BLL/Authentication/AuthContracts.cs)

### 1B. Read the authenticated Sales context

Open **`2. Current user`**. Send `GET {{baseUrl}}/api/auth/me` with `Authorization: Bearer {{accessToken}}`. There is **no body**. An illustrative HTTP 200 response is:

```json
{
  "userId": "<Identity user UUID>",
  "userName": "test.sales.mohamed",
  "employeeId": "<Employee UUID>",
  "employeeName": "<employee name>",
  "roles": ["Sales"],
  "permissions": [
    "Members.Create",
    "Members.OwnSalesCustomers",
    "Shifts.Manage",
    "Shifts.View"
  ],
  "currentBranch": {
    "id": "<branch UUID>",
    "name": "<branch name>"
  },
  "currentBranchId": "<same branch UUID>"
}
```

The permissions shown are examples, **not a claim about your current grants**. Confirm that `currentBranch.id` is non-null. Copy it into both `branchId` and `memberRegistrationBranchId`. Save `employeeId` to compare with the Member's Sales owner in Step 6. If `currentBranch` is null, the employee needs a valid branch assignment through the existing administration workflow. Do not guess the branch ID. Confirm the real `permissions` include `Members.Create`, `Members.OwnSalesCustomers`, and `Shifts.Manage` before continuing. [UserContextService.cs](../CampionsSystem.BLL/Authentication/UserContextService.cs) · [MemberManagementService.Create.cs](../CampionsSystem.BLL/Members/MemberManagementService.Create.cs)

## Step 2 — As Owner, find or create the branch Cash account

### 2A. Switch to the Owner account

Open **`1. Login`** again and log in with the Owner account. Replace `{{accessToken}}` with the **Owner** token; retain the `branchId` obtained from Sales. Open **`2. Current user`** to confirm the Owner identity and effective permissions. Creating an account requires `Branches.Manage` **and** `Branches.AccessAll`. Listing accounts requires `Payments.View` and branch access. A role name alone does not override Deny or branch restrictions. [FinancialAccountsController.cs](../CampionsSystem.API/Controllers/FinancialAccountsController.cs) · [PermissionService.cs](../CampionsSystem.BLL/Authentication/PermissionService.cs)

### 2B. Look for an existing Cash account first

Open **`15. Sales and Payments → Owner: active branch accounts for drawer setup`**.

| Setting | Value |
|---|---|
| Method and URL | `GET {{baseUrl}}/api/financial-accounts?branchId={{branchId}}` |
| Account and header | Owner; `Authorization: Bearer {{accessToken}}` |
| Body | None |
| Permission | `Payments.View` plus branch access |

The checked-in request may use `{{ownerToken}}`. For manual testing, either set `ownerToken` to the **current** Owner token or change that request's Bearer field to `{{accessToken}}`. The Owner may have no default `currentBranch`, so the explicit `branchId` query parameter is important. HTTP 200 returns `[]` when the branch has no active Cash/InstaPay accounts, or an array shaped like:

```json
[
  {
    "id": "<Cash account UUID>",
    "branchId": "<branch UUID>",
    "name": "Branch Cash",
    "method": "Cash",
    "isActive": true
  },
  {
    "id": "<InstaPay account UUID>",
    "branchId": "<branch UUID>",
    "name": "Branch InstaPay",
    "method": "InstaPay",
    "isActive": true
  }
]
```

If there is an **active** `Cash` item for the **same branch**, copy that item's `id` to `cashAccountId` and skip 2C. Do not copy the InstaPay item's ID. This GET provides IDs and metadata, **not balances**, and does not configure a drawer or open a Shift. `400 Select an operational branch.` means no usable branch selector reached the service. A 403 indicates missing effective `Payments.View` or branch scope. [SalesService.Accounts.cs](../CampionsSystem.BLL/Sales/SalesService.Accounts.cs)

### 2C. Create Cash only if none exists

Open **`15. Sales and Payments → Provision zero-opening Cash (global management)`**.

| Setting | Value |
|---|---|
| Method and URL | `POST {{baseUrl}}/api/financial-accounts` |
| Account and headers | Owner; `Authorization: Bearer {{accessToken}}`; `Content-Type: application/json` |
| Permission | `Branches.Manage` and `Branches.AccessAll` |
| Body | Raw JSON below |

If the collection request still uses `{{ownerToken}}`, point it to the current Owner token as described in 2B.

```json
{
  "name": "Branch Cash",
  "method": 0,
  "branchId": "{{branchId}}"
}
```

| Field | Type and requirement | Meaning |
|---|---|---|
| `name` | Required, non-blank string, at most 256 characters | Name within the branch; the same active name and method returns the existing account |
| `method` | Required enum | `0` = Cash; `1` = InstaPay. This API rejects Bank/Card/Wallet even though the underlying enum contains them |
| `branchId` | UUID; optional in the DTO but **supply it for an Owner without a current branch** | Copy the Sales employee's branch ID from Step 1; never generate it |

Expected HTTP 200 response shape:

```json
{
  "id": "<new Cash account UUID>",
  "branchId": "<branch UUID>",
  "name": "Branch Cash",
  "method": "Cash",
  "isActive": true
}
```

Copy the returned `id` into `cashAccountId`. Verify `branchId` and `method`. The account starts with `OpeningBalance = 0`; **creating it does not configure the Shared Drawer or move money**. You may later create an InstaPay account with `method: 1` if you want InstaPay payments, but it is not required just to register the first Member. A 400 may mean an invalid name/method/branch or an inactive branch; 403 means effective access is missing. [SalesService.Accounts.cs](../CampionsSystem.BLL/Sales/SalesService.Accounts.cs) · [SalesContracts.cs](../CampionsSystem.BLL/Sales/SalesContracts.cs)

## Step 3 — As Owner, configure the Shared Drawer once

**Count the real cash in that branch drawer before sending.** Set `drawerCount = 0` only if it is physically empty. If the drawer actually contains EGP 1,000, set `drawerCount = 1000.00`. The collection's `100000` is a placeholder and must not be used without a matching physical count. Generate and retain a new UUID for `drawerSetupOperationId`.

Open **`16. Employee shifts, shared vault, expenses and advances → Global audited drawer setup (once)`**.

| Setting | Value |
|---|---|
| Method and URL | `POST {{baseUrl}}/api/vault/setup` |
| Account and headers | Owner; `Authorization: Bearer {{accessToken}}`; `Content-Type: application/json` |
| Permissions | `Vault.Manage` **and** `Branches.AccessAll`, with branch scope; no employee Shift is required for setup |
| Body | Raw JSON below |

```json
{
  "branchId": "{{branchId}}",
  "operationId": "{{drawerSetupOperationId}}",
  "financialAccountId": "{{cashAccountId}}",
  "countedCash": {{drawerCount}},
  "reason": "Initial physical cash count for Testing Branch A"
}
```

| Field | Type and requirement | Meaning |
|---|---|---|
| `branchId` | UUID; optional in the DTO but **needed for an Owner without a current branch** | The same branch ID from Step 1 |
| `operationId` | Required nonzero UUID | Generated by you for this setup; keep it and the exact body for a retry |
| `financialAccountId` | UUID identifying an account | Copy `cashAccountId` from 2B or 2C; must be active Cash in this branch |
| `countedCash` | Nonnegative decimal, at most two decimal places | The real physical count; a JSON **number**, without quotes |
| `reason` | Required nonblank string, at most 2,000 characters | Why this initial cash observation was recorded |

For a **new, zero-opening account with no previous ledger entries** and an actual EGP 1,000 count, an illustrative HTTP 200 response is:

```json
{
  "branchId": "<branch UUID>",
  "accountId": "<same UUID as cashAccountId>",
  "bookCash": 1000.00,
  "expectedPhysicalCash": 1000.00,
  "lastCountedCash": 1000.00,
  "movementSequence": 1,
  "lastCountId": "<CashCount UUID>",
  "observedDiscrepancies": 0.00
}
```

These figures are **not verified results**. With a truly empty new drawer, monetary values are zero and the movement sequence may be zero. An account with existing ledger history can yield different book and discrepancy values. Verify `branchId` and `accountId` in the actual response. There is **no separate drawerId GUID**; the `CashDrawers` table uses `BranchId` as its primary key. If the first count is positive and the linked account has zero opening balance and no ledger entries, setup posts one `InitialPosition` credit with a note that it is **not Sales revenue**. It does not create a sale. [VaultService.cs](../CampionsSystem.BLL/Shifts/VaultService.cs) · [CashDrawerConfiguration.cs](../CampionsSystem.DAL/Configurations/CashDrawerConfiguration.cs)

If you get `400 Branch drawer is already configured`, **do not retry setup with a new UUID**. Use the position GET or a later physical count instead. `400 Select an active Cash account of this branch.` means the supplied account ID is missing, inactive, InstaPay, or from another branch. A 403 means `Vault.Manage`, `Branches.AccessAll`, or scope is missing.

**Optional verification:** Open **`16 → Shared drawer position`** and send `GET {{baseUrl}}/api/vault/position?branchId={{branchId}}` as Owner with Bearer token, no body. It requires `Vault.View` and returns the current `DrawerPosition` shape above. A later transaction may change its amounts. If your Owner gets 403 because `Vault.View` is ungranted, the successful setup response is still evidence of setup; this guide does not change grants. [VaultController.cs](../CampionsSystem.API/Controllers/VaultController.cs) · [FinancialOperations.cs](../CampionsSystem.BLL/Shifts/FinancialOperations.cs)

## Step 4 — Sales opens their **own** Shift

Log in again using **`1. Login`** as Sales, replace `{{accessToken}}` with that Sales token, and use **`2. Current user`** to confirm the expected `currentBranch.id` and effective `Shifts.Manage`. An Owner token does **not** open a Shift on behalf of the Sales employee: the backend uses the authenticated user's linked Employee.

First open **`16 → My open shift`**: `GET {{baseUrl}}/api/shifts/current` with Sales Bearer token, no body, requiring `Shifts.View`. If a Shift already exists, copy its `id` and `version` and **do not create another**. If none exists, the service returns null; ASP.NET may represent that as `204 No Content`. [ShiftService.cs](../CampionsSystem.BLL/Shifts/ShiftService.cs)

If none is open, count the **whole shared drawer again**. It may have changed since Owner setup. Open **`16 → Open my own shift`**.

| Setting | Value |
|---|---|
| Method and URL | `POST {{baseUrl}}/api/shifts` |
| Account and headers | Sales; `Authorization: Bearer {{accessToken}}`; `Content-Type: application/json` |
| Permission | `Shifts.Manage`, active linked Employee assigned to this branch, configured drawer |
| Body | Raw JSON below |

```json
{
  "operationId": "{{shiftOpenOperationId}}",
  "openingCash": {{drawerCount}}
}
```

| Field | Type and requirement | Meaning |
|---|---|---|
| `operationId` | Required nonzero UUID | New ID, **different from drawerSetupOperationId**; retain it only for an exact retry |
| `openingCash` | Nonnegative decimal, at most two decimal places | Current physical count of the **entire shared drawer**, not money owned by Sales |
| `branchId` | Optional UUID, omitted in this example | With Sales it defaults to the trusted `currentBranch.id`; any explicit value must be authorized |

An illustrative successful HTTP 200 `ShiftDetails` response for an EGP 1,000 drawer is:

```json
{
  "id": "<Shift UUID>",
  "branchId": "<branch UUID>",
  "employeeId": "<Sales Employee UUID>",
  "employeeName": "<Sales employee name>",
  "status": 0,
  "version": 1,
  "openedAt": "<UTC timestamp>",
  "closedAt": null,
  "openingBusinessDate": "<YYYY-MM-DD>",
  "closingBusinessDate": null,
  "openingCash": 1000.00,
  "expectedClosingCash": null,
  "actualClosingCash": null,
  "difference": null,
  "closedByUserId": null,
  "closingReason": null,
  "closureType": null,
  "verificationStatus": null,
  "closingAccountBalances": null,
  "closingCashBookBalance": null,
  "closingInstaPayBookBalance": null
}
```

`status: 0` means Open in the enum. Copy `id` to `shiftId` and `version` to `shiftVersion`. Verify with **`16 → My open shift`** that it returns the same ID. Common 400 errors: `Configure the branch shared drawer first` means Step 3 did not succeed for this branch; `You already have an open shift` means use the current Shift; `Open the next branch financial month...` means this branch uses FinancialMonths and lacks a valid open month. A 403 indicates missing effective permission or branch scope. **You do not have to open an explicit BusinessDay first**; when none is open, the backend uses today's Africa/Cairo date. [ShiftService.cs](../CampionsSystem.BLL/Shifts/ShiftService.cs) · [FinancialMonthPosting.cs](../CampionsSystem.BLL/MonthlyFinance/FinancialMonthPosting.cs)

## Step 5 — Sales registers a new Member

Set `memberFullName` to a clearly synthetic testing name and `memberPrimaryPhone` to a **new** testing phone that no Member or Lead already uses. If the branch lacks a `CountryCallingCode`, use a valid international `+...` phone format; a local Egyptian `01...` format requires the branch's country calling code. Do not copy a real customer's personal information into this guide or logs.

Open **`6. Member management → Create normal Sales member / cross-branch referral`**.

| Setting | Value |
|---|---|
| Method and URL | `POST {{baseUrl}}/api/members` |
| Account and headers | Sales; `Authorization: Bearer {{accessToken}}`; `Content-Type: application/json` |
| Permissions and prerequisites | `Members.Create`, `Members.OwnSalesCustomers`, active linked Employee, own open Shift in the operational branch, configured drawer |
| Body | Raw JSON below |

```json
{
  "fullName": "{{memberFullName}}",
  "primaryPhone": "{{memberPrimaryPhone}}",
  "secondaryPhone": null,
  "dateOfBirth": null,
  "gender": null,
  "notes": "Manual testing member registration",
  "targetRegistrationBranchId": "{{memberRegistrationBranchId}}",
  "creationType": "NormalSales"
}
```

| Field | Type and requirement | Meaning and validation |
|---|---|---|
| `fullName` | Required nonblank string, at most 256 characters | Member's name |
| `primaryPhone` | Required string, at most 64 characters; valid and unique after normalization | International `+...`, or local format if the registration branch has `CountryCallingCode`; an existing Lead with the number must be converted rather than duplicated |
| `secondaryPhone` | Optional nullable string, at most 64 characters | Additional phone |
| `dateOfBirth` | Optional nullable `YYYY-MM-DD` | Cannot be in the future |
| `gender` | Optional nullable string, at most 32 characters | Free text; no enum in this DTO |
| `notes` | Optional nullable string, at most 4,096 characters | Notes |
| `targetRegistrationBranchId` | Required nonzero UUID | For this exercise, **same value as** `branchId` from Step 1 |
| `creationType` | Required string enum | Exactly `"NormalSales"` here; the other values are `FreelanceHouse` and `ManagementCreated`, each with different rules |

Do **not** add `salesEmployeeId` or `freelancePlanId` for `NormalSales`. The service chooses the authenticated Sales employee as owner and rejects explicit owner/plan values. This registration does **not** create a subscription, sale, payment, or financial ledger entry. [MemberManagementService.Create.cs](../CampionsSystem.BLL/Members/MemberManagementService.Create.cs)

```json
  "secondaryPhone": null,

  },

    "id": "<assignment UUID>",
    "salesEmployeeId": "<Sales Employee UUID>",
    "salesEmployeeName": "<Sales employee name>",

  },

```

The `clientCode: 1` is only an example; the real value is branch-local and generated by the backend. Current `memberCode` values are GUID-style, not human-readable sequential numbers. Copy `id` into `memberId`, then continue to Step 6. `400 Configure...` means Drawer missing; `400 Open your own employee shift...` means Shift missing; an existing Lead phone calls for Lead conversion; 403 indicates effective `Members.Create`/`Members.OwnSalesCustomers` or branch-scope denial. [MemberContracts.cs](../CampionsSystem.BLL/Members/MemberContracts.cs) · [PhoneNormalizer.cs](../CampionsSystem.BLL/Members/PhoneNormalizer.cs)

## Step 6 — Verify the Member and Sales assignment

With the same Sales token:

1. Open **`6 → Member details`**. Send `GET {{baseUrl}}/api/members/{{memberId}}` with `Authorization: Bearer {{accessToken}}`, no body, requiring `Members.View`. Expect HTTP 200 with the `MemberDetails` shape above. Check `registrationBranch.id == branchId` and `currentSalesOwner.salesEmployeeId == employeeId` from Step 1.
2. Open **`6 → Current Sales assignment`**. Send `GET {{baseUrl}}/api/members/{{memberId}}/sales-assignment` with the same bearer token, no body, requiring `Members.View`. Expect HTTP 200 with an assignment shaped like `{"id":"<assignment UUID>","salesEmployeeId":"<Employee UUID>","salesEmployeeName":"<name>","assignedAt":"<timestamp>","endedAt":null,"reason":"Registration"}`. If a Member is House, this service returns null, which ASP.NET may present without a JSON body.

A successful Member GET proves the profile exists; it does **not** prove any subscription, payment, or Check-In exists. A 404 may mean the ID is wrong or the Member is outside your branch scope. A 403 points to effective `Members.View` or branch access. [MembersController.cs](../CampionsSystem.API/Controllers/MembersController.cs) · [MemberManagementService.Sales.cs](../CampionsSystem.BLL/Members/MemberManagementService.Sales.cs)

## Troubleshooting HTTP responses

| Response | What it means here | What to check manually |
|---|---|---|
| `400 Configure the branch shared drawer first.` | No `CashDrawers` record exists for the operational branch, **even if a Cash account exists** | Confirm Owner completed Step 3 for the same branch as Sales |
| `400 Select an operational branch.` | An Owner with no default branch sent a branch-sensitive request without a resolved branch selector | Put `?branchId={{branchId}}` on the GET or `"branchId":"{{branchId}}"` in setup JSON |
| `400 Select an active Cash account of this branch.` | The setup account ID is missing, inactive, InstaPay, or belongs to another branch | List the branch accounts and copy the active `Cash` item's `id` |
| `400 Open your own employee shift...` | Drawer exists, but the actual logged-in employee lacks an eligible open Shift | Log in as that employee and complete Step 4 |
| Other Member `400` | Invalid/duplicate phone, an existing Lead, invalid profile, missing country code, or a wrong creation type | Read the ProblemDetails `title` and correct that specific condition |
| `401` | Missing/expired token or rejected login | Log in again and check the **request's own Authorization tab**; do not mix `ownerToken` with `accessToken` |
| `403` | Missing effective capability, Deny override, branch-scope denial, or a creation type the actor cannot use | Compare `/api/auth/me.permissions` and `currentBranch.id` with the selected request/body; this guide does not alter grants |
| `404` | The referenced record is missing or outside accessible scope | Copy the ID from the previous successful response and verify the branch |
| `409` | Concurrent/unique conflict or stale Shift version | GET the current record/version; use the same operation ID only for an exact retry, a new ID for a new action |

The backend usually returns a ProblemDetails `title` for business errors, with 403 for service authorization failure. Save the **status and title** when troubleshooting; a trace ID by itself does not explain the cause. [BranchControllerBase.cs](../CampionsSystem.API/Controllers/BranchControllerBase.cs)

## What each business concept means

| Concept | Purpose and example | Who creates or manages it; frequency |
|---|---|---|
| Financial Account / Cash Account | Branch A can have a `Branch Cash` account and a separate `Branch InstaPay` account. Book balance = `OpeningBalance + Credits − Debits`. | An account-management user with `Branches.Manage` and `Branches.AccessAll` creates accounts during setup; not every day. The API allows multiple differently named Cash accounts, but only one Cash account can be linked to the branch Drawer. [SalesService.Accounts.cs](../CampionsSystem.BLL/Sales/SalesService.Accounts.cs) |
| Shared Drawer / Drawer Configuration | **One physical Cash drawer per branch** shared by Mohamed and Ahmed. `CashDrawers` connects a branch to one Cash account; it is not an employee-owned wallet. | `Vault.Manage` + `Branches.AccessAll` configures it once per branch with `POST /api/vault/setup`. There is no visible reconfiguration endpoint; later counts observe physical state. [CashDrawerConfiguration.cs](../CampionsSystem.DAL/Configurations/CashDrawerConfiguration.cs) · [VaultService.cs](../CampionsSystem.BLL/Shifts/VaultService.cs) |
| Initial and Shift-opening cash | `countedCash` at setup records the initial physical count. `openingCash` at each Shift opening records the **whole drawer** at that time. | Initial setup once; each employee manually opens each new Shift with a current shared-drawer count. These are distinct observations, not separate deposits. [ShiftService.cs](../CampionsSystem.BLL/Shifts/ShiftService.cs) |
| Employee Shift | A work interval tied to the actual employee/user and branch; multiple employees can have overlapping Shifts. | An eligible employee with `Shifts.Manage` opens **their own** Shift. Normal self-close requires an actual count. A properly authorized Owner/BranchManager may close someone else's Shift with a reason; omitting the count marks it `Unverified`. [ShiftService.cs](../CampionsSystem.BLL/Shifts/ShiftService.cs) |
| Business Day | Optional explicit accounting date for branch operations, which can differ from the wall clock date. Without an open BusinessDay, the service uses the current date in `Africa/Cairo`. | `Shifts.Manage` opens/closes an explicit day when needed. It is **not required** before a Shift or Member registration. Closing a BusinessDay does not close Shifts. [FinancialOperations.cs](../CampionsSystem.BLL/Shifts/FinancialOperations.cs) |
| Cash Reconciliation | A count compares actual physical Cash with the expected physical Cash: `difference = countedCash − expectedPhysicalCash`. Negative is a shortage; positive is a surplus. | Setup, Shift opening/closing, or `POST /api/vault/counts` creates a `CashCount` observation. A count does not create an expense or payment and does not silently change the book balance. [FinancialOperations.cs](../CampionsSystem.BLL/Shifts/FinancialOperations.cs) |

| Cash versus InstaPay | Cash is physical money in the shared drawer. ### Initial setup versus daily work

**Once per branch:** ensure the branch is active and staff have the correct assignments. Find or create its Cash account (and optionally an InstaPay account). Configure its Shared Drawer using the actual cash count. Creating Cash and InstaPay accounts with zero opening balances **does not** create the Drawer. Once configured, `POST /api/vault/setup` refuses a second Drawer for that branch. There is no public route in this controller to switch the Drawer to a different Cash account. [FinancialAccountsController.cs](../CampionsSystem.API/Controllers/FinancialAccountsController.cs) · [VaultService.cs](../CampionsSystem.BLL/Shifts/VaultService.cs)

**For each work Shift:** the eligible employee counts the shared drawer, opens their own Shift, performs authorized operations, reviews personal and branch-period reports, and closes their own Shift with a real count. Opening an explicit BusinessDay is optional. If you open one, close it at the appropriate time; otherwise its BusinessDate continues to be used even after midnight. If the branch already uses FinancialMonths, the next Shift or financial posting also needs an applicable open financial month. [ShiftService.cs](../CampionsSystem.BLL/Shifts/ShiftService.cs) · [FinancialMonthPosting.cs](../CampionsSystem.BLL/MonthlyFinance/FinancialMonthPosting.cs)

### Example: two overlapping Shifts, one shared drawer

Assume Branch A starts with **EGP 1,000** physical and book Cash. Mohamed opens his Shift at 9:00 and counts the entire drawer at 1,000. Ahmed opens a separate Shift at 10:00 and counts the **same drawer**, not a new one, at 1,000. Mohamed receives EGP 500 Cash; Ahmed receives EGP 300 Cash. With no other movements, before Mohamed closes at 17:00 the shared Cash book and expected physical position are **EGP 1,800**. Mohamed's own Shift-linked inflow is 500. Ahmed's is 300. Mohamed's `branchPeriod` report includes both inflows, 800 total, because they occurred in his Shift time window.

If Mohamed counts EGP 1,800 and closes, his count discrepancy is zero, but Ahmed's Shift remains open and the shared drawer is **not reset**. If Mohamed instead counts EGP 1,750, the system records a **−50** CashCount discrepancy; the Cash account's **book balance remains 1,800**. The latest physical observation becomes the basis for subsequent expected physical Cash. Never add the two employees' `openingCash` values as if EGP 2,000 was collected. [FinancialOperations.cs](../CampionsSystem.BLL/Shifts/FinancialOperations.cs) · [ShiftReportService.cs](../CampionsSystem.BLL/Shifts/ShiftReportService.cs)

At 23:00 the remaining employee can close their own Shift after counting the full shared drawer. An authorized Owner/BranchManager can close another employee's Shift using `close-override` with a reason; if no physical count is supplied, the closure is `Unverified` and counted Cash/difference stay null. The backend does **not** automatically close a Shift at midnight. It does not make closing the explicit BusinessDay dependent on every Shift being closed, though Monthly Closing does require all branch Shifts closed. If a Shift is left open overnight, the same employee cannot open a second Shift until that one is closed. **Operational recommendation, not an automatic API rule:** review open Shifts and any explicit BusinessDay at day's end. [ShiftService.cs](../CampionsSystem.BLL/Shifts/ShiftService.cs) · [MonthlyFinanceService.cs](../CampionsSystem.BLL/MonthlyFinance/MonthlyFinanceService.cs)

## Exact cause of “Configure the branch shared drawer first”

`MembersController.Create` calls `MemberManagementService.CreateMemberAsync`. After permission, profile, creation-type and branch checks, `CreateCoreAsync` calls `FinancialOperations.LockBranchAsync` for the employee's operational branch **before** `RequireShiftAsync`. If that branch has no `CashDrawers` row, `LockBranchAsync` throws the exact message `Configure the branch shared drawer first.` and the API returns HTTP 400. Merely having Cash and InstaPay `FinancialAccounts` does **not** create that Drawer row.

The operational sequence is therefore **Cash account → Owner drawer setup for Sales's branch → Sales own Shift → Member registration**. After the Drawer exists, a missing Shift produces a different error: `Open your own employee shift at this branch before performing this operation.` This is source-verified. Whether your Testing branch is configured *right now* is not verified by this guide because no API or database request was made. ## Four practical scenarios

1. **A — Owner prepares a new branch.** Sales logs in and copies `currentBranch.id` from `/api/auth/me`. Owner logs in, lists that branch's accounts, creates Cash only if missing, then calls `POST /api/vault/setup` with the Cash ID and a real count. Verify `branchId` and `accountId` in the response. Do not repeat setup daily.
2. **B — Sales opens a Shift and registers the first Member.** Sales logs in and checks `GET /api/shifts/current`. If no Shift exists, Sales counts the shared drawer and calls `POST /api/shifts` with a new operation ID. Copy the Shift ID. Then call `POST /api/members` with `creationType: "NormalSales"` and the same registration branch. Verify with Member details and current Sales assignment. No Sale or Payment is created.
3. **C — Two employees work concurrently.** Each logs in separately and opens **their own** Shift after observing the same shared drawer. After actual financial operations, inspect each Shift's `summary`, own `transactions`, and full `branch-transactions`. Each employee closes their own Shift using its current `expectedVersion` and a real count of the **entire** drawer. If one is absent, an authorized Owner/Manager can `close-override` with a reason and omit count; it remains `Unverified`. Close an explicit BusinessDay only if one was opened.
4. **D — The next day.** Do not create another Cash account or Drawer. Check `GET /api/business-days/current?branchId=...` and `GET /api/shifts/current`. Close an overnight Shift through an authorized route. If you use explicit BusinessDays, close the prior day and open a valid later date; otherwise the backend uses today's Cairo date. Each employee starts a new Shift with a new operation ID and current physical count. If FinancialMonths have been configured, ensure an applicable month is open.

**Key result:** A Cash FinancialAccount, a configured Shared Drawer, and an employee's open Shift are **three separate prerequisites**. The registration blocker is the missing Drawer record for the operational branch, checked before Shift eligibility. Every Postman step here is for you to execute and verify; none was performed while writing this guide.
