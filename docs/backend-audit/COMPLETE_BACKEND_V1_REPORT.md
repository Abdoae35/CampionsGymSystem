## Executive summary

The backend is a substantial ASP.NET Core controller API with 231 application operations in 29 controller groups. It covers Identity and Owner access administration; branches and employees; CRM and members; membership plans and subscriptions; gym check-in; Sales, split payments, installments, refunds and Quick Cancel; shared branch drawer, Shifts and expenses; Sales commissions; Private and Classes operations; coach earnings and partial payouts; salary, payroll and branch monthly closing; informational periodic expense planning; and XLSX bulk registration. A Development-only database health operation brings the OpenAPI count to 232. The only public application action is login. Four legacy write routes deliberately return HTTP 410. The code has 31 EF migration classes; the last adds ExcelImportBatches and ExcelImportRows. A fully migrated model has 114 tables including seven ASP.NET Identity tables and EF history, according to the migration delta and the last documented Development/Testing verification. The older database guide still describes its earlier 112-table/27-migration baseline and must not be treated as the current model. No live database count was rerun here. ## System architecture and execution model

The solution uses CampionsSystem.API for routing, JWT authentication, authorization and HTTP error translation; CampionsSystem.BLL for domain workflows, permission/branch checks, locking, financial orchestration and DTO contracts; and CampionsSystem.DAL for entities, EF configurations, DbContext and migrations. ApplicationDbContext uses PostgreSQL via Npgsql and loads entity configurations from its assembly. The connection key is ConnectionStrings:DefaultConnection; the source requires an externally configured value rather than embedding a password. Identity is registered with Guid users and roles. [Program.cs](../../CampionsSystem.API/Program.cs#L20), [ApplicationDbContext](../../CampionsSystem.DAL/Data/ApplicationDbContext.cs#L11).

The typical request path is controller attribute authorization → BLL service effective access/branch check → entity and business validation → transaction/locks for mutations → EF persistence plus AuditLog → DTO or ProblemDetails response. BranchControllerBase maps unauthorized service calls to 403, missing branch-related records to 404, business rules to 400, and concurrency/duplicate/serialization conflicts to 409. Login returns 401 for invalid credentials. Individual controllers have additional response behavior, including 410 for disabled routes. [BranchControllerBase](../../CampionsSystem.API/Controllers/BranchControllerBase.cs#L9), [AuthController](../../CampionsSystem.API/Controllers/AuthController.cs#L10), [OperationsController](../../CampionsSystem.API/Controllers/OperationsController.cs#L50).

Financial mutations coordinate through FinancialOperations: a database transaction and branch advisory lock serialize shared-drawer postings and Shift state. The ledger is FinancialTransactions; PaymentParts and RefundParts describe tender splits but are not extra ledger money. FinancialMonthPosting routes new operations to an open branch financial month when month lifecycle has been configured. [FinancialOperations](../../CampionsSystem.BLL/Shifts/FinancialOperations.cs#L14), [FinancialTransaction](../../CampionsSystem.DAL/Entities/FinancialTransaction.cs), [FinancialMonthPosting](../../CampionsSystem.BLL/MonthlyFinance/FinancialMonthPosting.cs#L8).

No hosted background worker or notification scheduler is registered in the inspected Program.cs. Planned-expense reminders are computed on request. The source uses manual HTTP-triggered operations and inline transactional processing; this audit found no separate message broker, CQRS handler or payment gateway. [Program.cs](../../CampionsSystem.API/Program.cs#L34), [MaintenanceService](../../CampionsSystem.BLL/MonthlyFinance/MaintenanceService.cs#L92).

## Implemented business workflows

The paths below state preconditions, action, service sequence, state and financial consequence. Each write path returns a business/authorization/concurrency error through its controller if a precondition fails; the transaction-based paths roll back their writes on exception. Specific DTO fields and HTTP methods are catalogued operation by operation.

### 1. Login, identity and privileged access

POST /api/auth/login validates Identity credentials, account status and linked employee eligibility before issuing a signed JWT. GET /api/auth/me resolves live roles, effective permissions and current branch; JWT validation uses issuer, audience, lifetime and signing-key checks, with ActiveUserJwtEvents refreshing account eligibility on requests. A disabled or locked account, or a linked suspended/terminated employee, has no usable current context. Owner access administration requires the Owner-specific policy plus the relevant Roles/Users capability. Role membership, role grants and per-user overrides write audit evidence; Deny removes a capability even when roles grant it. OwnerAccountProtection serializes changes and prevents losing the last usable Owner or an Owner disabling themselves through employee lifecycle. No role label alone grants generic permission administration. [AuthController](../../CampionsSystem.API/Controllers/AuthController.cs#L10), [AuthenticationRegistration](../../CampionsSystem.API/Authentication/AuthenticationRegistration.cs#L13), [UserContextService](../../CampionsSystem.BLL/Authentication/UserContextService.cs#L13), [PermissionService](../../CampionsSystem.BLL/Authentication/PermissionService.cs#L7), [OwnerAccountProtection](../../CampionsSystem.BLL/Authentication/OwnerAccountProtection.cs#L11).

### 2. Branch, employee and commercial assignment

An authorized manager/Owner creates or updates branch and employee records through the relevant APIs; BLL services validate employment and branch scope and maintain effective-dated assignments. Transfers preserve assignment history and are checked against open Shift/payroll conditions. An employee account may have multiple Identity roles, while commercial Sales ownership is a separate MemberSalesAssignment/LeadAssignment fact. Thus an authorized Manager who is also a Sales employee can own personally assigned customers without receiving branch-wide commission. Changing role grants does not rewrite historical assignment rows. [EmployeeBranchAssignmentService](../../CampionsSystem.BLL/Branches/EmployeeBranchAssignmentService.cs), [MemberManagementService.Sales](../../CampionsSystem.BLL/Members/MemberManagementService.Sales.cs), [BranchAccessService](../../CampionsSystem.BLL/Branches/BranchAccessService.cs#L15).

### 3. Leads, manual members and Excel Import

POST /api/leads creates a phone-first lead after normalization and duplicate search; assignment and interaction endpoints track follow-up history, and conversion creates a Member through the existing member rules. Manual POST /api/members uses creation type (NormalSales, ManagementCreated or FreelanceHouse) and requires an eligible operator Shift for registration. Its chosen/derived Sales owner and branch are validated; a profile alone does not sell a plan. Excel template GET supplies three distinct XLSX layouts. Preview POST parses at most 1 MiB/100 rows, rejects formulas/macros/external links, normalizes phones, detects in-file and existing duplicates, and saves a short-lived server-owned import batch and per-row preview evidence, but creates no Lead/Member. Confirmation POST reloads the batch, checks authorization and Shift again, calls the normal Lead/Member services per eligible row, records individual outcomes, and makes retries idempotent. It deliberately creates no subscription, payment or ledger transaction. The batch/result is queryable by its creator until expiration. [LeadManagementService.Create](../../CampionsSystem.BLL/Crm/LeadManagementService.Create.cs#L12), [MemberManagementService.Create](../../CampionsSystem.BLL/Members/MemberManagementService.Create.cs), [ExcelImportWorkbook](../../CampionsSystem.BLL/Imports/ExcelImportWorkbook.cs#L11), [ExcelImportService](../../CampionsSystem.BLL/Imports/ExcelImportService.cs#L30).

### 4. Plans, paid subscriptions and check-in

Management configures MembershipPlans, categories, benefits, offer eligibility and eligible-member lists. A sale of a membership creates purchase snapshots and a regular MemberSubscription grant; renewals add documented entitlement rather than mutating past price evidence. Freeze and holiday/custom extension paths record their own history. Reception POST /api/check-ins evaluates current member, plan entitlement, BusinessDate, branch/city rules, remaining visits and duplicate entry before writing a CheckIn. Trial redemption and borrowed-session variants have separate evidence; this audit found no current GuestInvitation issuance action, so trial issuance is a distinct gap. A normal gym check-in does not consume Private or Classes package sessions. [MembershipPlanManagementService](../../CampionsSystem.BLL/Plans/MembershipPlanManagementService.cs), [SubscriptionService.PaidSales](../../CampionsSystem.BLL/Subscriptions/SubscriptionService.PaidSales.cs), [CheckInService.Entry](../../CampionsSystem.BLL/CheckIns/CheckInService.Entry.cs#L36).

### 5. Sale, collection, installment, refund and cancellation

POST /api/sales validates offer/plan/member/branch and creates a SaleTransaction with purchaser category and commercial owner snapshot; payment may be collected immediately or later. POST /api/sales/{id}/payments locks the sale, checks a caller OperationId for exact retries, validates amount and Cash/InstaPay parts, associates an actual eligible Shift, creates Payment/PaymentParts and posts one FinancialTransaction credit per account grouping. The Sale status is Open until net collection equals the sale amount, then Completed. Installment allocations are separate evidence, not duplicate cash. [SalesService.Payments](../../CampionsSystem.BLL/Sales/SalesService.Payments.cs#L8), [FinancialOperations](../../CampionsSystem.BLL/Shifts/FinancialOperations.cs#L129).

Quick Cancel requires the Reception role and Sales.QuickCancel, an open operator Shift, an uncancelled sale and server-clock age no greater than 24 hours. The caller explicitly chooses a refund of zero, part or all; attendance does not calculate the deduction. After that window the normal Sales.Refund path requires BranchManager role or Owner, relevant capability and branch scope. RefundCore caps amount at completed collection less prior refunds, checks coaching earnings/finalized-period restrictions, records Refund/RefundParts, allocates commission refund evidence, cancels the entitlement grant and posts account debits only for positive monetary parts. Zero-refund cancellation has no fictitious financial ledger row. Exact retry uses OperationId, request hash and actor. [QuickCancel](../../CampionsSystem.BLL/Sales/SalesService.QuickCancel.cs#L8), [Refunds](../../CampionsSystem.BLL/Sales/SalesService.Refunds.cs#L9).

### 6. Shifts, shared drawer, expenses and advances

Employees explicitly POST /api/shifts to open only their own Shift. An open Shift per employee is unique at database level. Reception money operations check the actual authenticated actor's active Shift within the serialized branch transaction. Normal self-closure records a physical count; authorized Owner/BranchManager with Shifts.CloseOthers may close another employee's open Shift in-scope, optionally without count. Missing count persists null counted/discrepancy with Unverified status and actor/reason; it is not a zero count. Closure snapshots account balances and does not post money. [ShiftService](../../CampionsSystem.BLL/Shifts/ShiftService.cs#L45), [ShiftConfiguration](../../CampionsSystem.DAL/Configurations/ShiftConfiguration.cs#L25).

One branch drawer is shared across overlapping employee Shifts. GET /api/shifts/{id}/transactions filters the employee's linked ledger rows. GET /api/shifts/{id}/branch-transactions and /summary instead show all branch movements in that Shift's interval, including other operators and Owner activity; the summary separates opening balance, account movements and expected closing balance, with a closure cutoff for historical Shifts. Physical CashCount observations record discrepancies but do not change book cash. Owner paid expenses can use the Owner actor without a fabricated Shift; other expense operators need their own Shift. Actual Expense, return and EmployeeAdvance movements post to FinancialTransactions. An advance is limited to that branch/period's prorated basic salary less earlier advances. [ShiftReportService](../../CampionsSystem.BLL/Shifts/ShiftReportService.cs#L42), [VaultService](../../CampionsSystem.BLL/Shifts/VaultService.cs#L46), [ExpenseService](../../CampionsSystem.BLL/Shifts/ExpenseService.cs#L20), [AdvanceService](../../CampionsSystem.BLL/Shifts/ExpenseService.Advances.cs#L14).

Example: a shared Cash account opens at EGP 10,000. Employee A collects 1,500, employee B collects 3,000 and pays a 500 expense. Book Cash becomes EGP 14,000. A's own Shift credit total remains 1,500; A's branch-period summary explains all 4,000 net branch movement without assigning B's activity to A. The service groups ledger records by account and operator and uses posting time for the interval. [ShiftReportService](../../CampionsSystem.BLL/Shifts/ShiftReportService.cs#L42).

### 7. Sales commissions and Manager-as-Sales

Commission periods and CommissionRules are configured by branch, employee and category: New Membership and Renewal are separate targets and below/reached rates. The service does not infer those rates from a Manager role. Completed Payment collections are joined to CommissionCollection/ownership evidence and reduced by refund allocations; House and excluded collections are displayed separately. An open-period progress is provisional. Finalize stores statement lines and EmployeeCommissionSummaries. Formula in code: earned commission = round(eligible net collection × configured applicable percentage / 100, 2 decimals, away from zero). For example, an eligible EGP 1,000 personal collection at a configured 5% gives EGP 50; the default percentage is not hardcoded by that formula. The employee who received a Payment is distinct from the Sales employee attributed the collection. [CommissionService.Calculation](../../CampionsSystem.BLL/Commissions/CommissionService.Calculation.cs#L10), [CommissionService](../../CampionsSystem.BLL/Commissions/CommissionService.cs#L57), [CommissionSources](../../CampionsSystem.BLL/Commissions/CommissionSources.cs).

### 8. Private coaching, Classes and coach payouts

A Private purchase snapshots package sessions, total net price, floor-to-cent unit value and remainder on the last session. A coach registers a Private session only when the buyer is active, has a valid regular membership, has a reception Gym CheckIn for the same BusinessDate/branch, has an eligible unexpired Private session and the actor is the assigned coach. One actual PrivateSession consumes one balance unit. Transfers close and create coach assignment history; delivered sessions keep their original coach. Owner expiry settlement records unused entitlement for earnings only, with no fake attendance. Recognition allocates only funded net collection, uses a configured per-coach Private target, applies 50% below and 60% at target to original-coach delivery, and fixed 50% to incoming-coach transferred-package delivery. Example: 10 sessions/EGP 1,000, two original-coach sessions represent EGP 200 and pay EGP 100 or EGP 120 at those rates; eight incoming-coach sessions represent EGP 800 and pay EGP 400. A partial Owner payout reduces outstanding and posts exactly one expense/ledger debit, distinct from earning recognition. [CoachingService](../../CampionsSystem.BLL/Coaching/CoachingService.cs#L18), [CoachingService.Earnings](../../CampionsSystem.BLL/Coaching/CoachingService.Earnings.cs#L46), [CoachingService.Payouts](../../CampionsSystem.BLL/Coaching/CoachingService.Payouts.cs#L10).

Classes packages use one shared remaining-session balance across class types. The coach registers each attendee directly before the scheduled occurrence starts; this path does not require a reception Gym CheckIn. It rejects repeat member/occurrence registrations, expired or empty packages and wrong coach/branch. Completed occurrences support attendance counts and actual average = valid attendance / completed eligible occurrences. The target threshold can be configured, but compensation is explicitly NotConfigured; no Classes payout formula is calculated. Legacy /api/classes/sessions write endpoints return 410 and direct callers to /api/coaching/classes/occurrences. [CoachingService.Classes](../../CampionsSystem.BLL/Coaching/CoachingService.Classes.cs#L33), [CoachingContracts](../../CampionsSystem.BLL/Coaching/CoachingContracts.cs#L55), [OperationsController](../../CampionsSystem.API/Controllers/OperationsController.cs#L50).

### 9. Salary, payroll, periodic planning and financial month closing

SalaryService stores dated EmployeeSalarySetting history. SalaryProjection iterates an inclusive branch month, applies employment status and branch assignment evidence, requires exactly one setting for an eligible day, divides the monthly rate by period days, and rounds cumulative daily entitlement so branch transfers preserve cents. Suspended/resigned days are excluded; approved leave is paid. For EGP 6,000 across a 30-day period with 15 eligible days, basic entitlement is EGP 3,000 before that branch's advances. Payroll recognizes basic entitlement and finalized Sales commission summaries separately. PayrollPaymentRecords record actual partial payments and outstanding but intentionally post no imaginary Cash/InstaPay ledger movement. [SalaryProjection](../../CampionsSystem.BLL/MonthlyFinance/SalaryProjection.cs#L15), [PayrollService](../../CampionsSystem.BLL/MonthlyFinance/PayrollService.cs#L15).

A branch financial month must have explicit inclusive start/end BusinessDates (1–62 days in the service) and follow its previous period. Closing obtains branch coordination, requires the month-end date and all branch Shifts closed, may accept a final physical recount, recognizes basic salary and any finalized Sales summaries, builds the report and six-sheet XLSX, then writes FinancialClosingRevision with JSON, workbook bytes and hash plus FinancialMonthEvent/AuditLog. The six sheets are Monthly Summary; All Financial Transactions; Sales Performance; Employee Salaries & Advances; Coaches - Private - Classes; Vault & Shifts. Reopening records a reason/event and retains old revisions; it does not reopen Sales/Coach commission statements or backdate new operations. FinancialMonthPosting directs later postings to the next open branch period while original occurrence evidence may be recorded separately. [MonthlyFinanceService](../../CampionsSystem.BLL/MonthlyFinance/MonthlyFinanceService.cs#L38), [MonthlyWorkbook](../../CampionsSystem.BLL/MonthlyFinance/MonthlyWorkbook.cs#L16), [FinancialMonthPosting](../../CampionsSystem.BLL/MonthlyFinance/FinancialMonthPosting.cs#L8).

MaintenancePlanRevisions hold branch, cost, interval, first/next expected date, active state, reason and revision. Suggestion = round(expected cost / frequency months, 2, away from zero); EGP 15,000 / 3 = EGP 5,000 per month. Summary and reminder reads show upcoming/overdue plans. This is informational only: it creates neither Expense nor FinancialTransaction nor a real reserve balance. Actual maintenance must be entered once through paid Expenses. [MaintenanceService](../../CampionsSystem.BLL/MonthlyFinance/MaintenanceService.cs#L13).

## Security and authorization

JWT Bearer, not a server cookie/session, is configured; issuance and validation use a required signing key, issuer/audience, expiry and 30-second clock skew. The active-user event and UserContextService make account/employee deactivation effective on later requests. Password policy has a 12-character minimum and lockout after five failed attempts for 15 minutes. The code does not implement token refresh in the inspected AuthController. [AuthenticationRegistration](../../CampionsSystem.API/Authentication/AuthenticationRegistration.cs#L13), [AuthController](../../CampionsSystem.API/Controllers/AuthController.cs#L10), [UserContextService](../../CampionsSystem.BLL/Authentication/UserContextService.cs#L13).

## Financial integrity and reporting rules

FinancialTransaction SourceType can be Payment, Refund, Expense, Payroll, Adjustment, EmployeeAdvance or CashMovement; direction is Credit/Debit. The actual code posts member collections as credits, refunds/paid expenses/advances/payout expenses as debits, and an actual returned expense as credit. A coach payout is represented by one Expense-linked debit, not both a coach and expense ledger debit. PayrollPaymentRecord is payment evidence without funding account/ledger movement. The enum contains Payroll and Adjustment categories, but their existence alone does not prove a current API path posts those source types; source-specific posting must be traced. [FinancialSourceType](../../CampionsSystem.DAL/Enums/FinancialSourceType.cs), [FinancialTransactionType](../../CampionsSystem.DAL/Enums/FinancialTransactionType.cs), [Refunds](../../CampionsSystem.BLL/Sales/SalesService.Refunds.cs#L68), [CoachPayouts](../../CampionsSystem.BLL/Coaching/CoachingService.Payouts.cs#L22), [PayrollService](../../CampionsSystem.BLL/MonthlyFinance/PayrollService.cs#L95).

Book account balance equals opening balance plus ledger credits minus debits. Counted physical cash is an observation, not a ledger adjustment; a discrepancy remains in the report. Shift reporting keeps employee-linked totals separate from all branch postings during the Shift window. Monthly transaction rows come from ledger records once, with linked PaymentParts, RefundParts, commission allocations, actor, Shift, customer, commercial Sales owner, provider reference, audit and reversal details used only as explanatory evidence. For inactive accounts, historical account type is still read from persisted FinancialAccount. [FinancialOperations](../../CampionsSystem.BLL/Shifts/FinancialOperations.cs#L81), [ShiftReportService](../../CampionsSystem.BLL/Shifts/ShiftReportService.cs#L42), [MonthlyReportBuilder.Transactions](../../CampionsSystem.BLL/MonthlyFinance/MonthlyReportBuilder.Transactions.cs#L8).

MonthlyReportBuilder limits each current-period detail dataset to 50,000 records and uses database-side aggregates for historical employee/coach opening obligations. The report selects the branch month's FinancialTransaction rows, not all old detailed transactions. Its stated net operating result is: net member collections − net ordinary paid operating expenses − prorated basic salary − newly recognized finalized Sales commission − newly recognized Private earnings. Employee payout records, coach payout debits, advances and planning suggestions are not subtracted again as earned cost. This blends a collection-based top line with selected earned obligations and is explicitly labeled in the DTO; it is not a formal accrual profit-and-loss statement. Idempotency and atomicity are source-specific, not blanket properties of every operation. Key Sales, Shift, expense, month, coach payout and import-confirmation mutations use OperationId/request evidence and transaction/locking or unique constraints; GETs do not need idempotency keys. For one concrete example, Quick Cancel checks OperationId and hash inside a transaction before a refund, while FinancialOperations locks the branch drawer before posting. Concurrency conflicts surface as 409 or service-specific 400 rather than silently double-posting. The catalog identifies mutating endpoints; a change review must still inspect the invoked method's transaction boundary. ## Frontend integration readiness

The React client can rely on the 231 routed application operations and current OpenAPI for DTO schemas, with the four 410 legacy operations excluded from new UI flows. Use the returned JWT as Bearer, call /api/auth/me after authentication and on reload as designed, drive controls from effective capabilities but let 401/403 remain authoritative, pass selected branch IDs only when the user has scope, and preserve OperationId on retries of mutating financial/import actions. Use server-side page/pageSize conventions (usually at most 100) and display ProblemDetails errors. Excel Import is template → preview → user review → confirm → result; do not treat preview rows or spreadsheet values as trusted state. ## Conclusion

The source implements the broad Backend V1 workflow and a comprehensive route surface, with financial evidence separated from planning suggestions and payment/earning concepts. It is ready for controlled frontend alignment and isolated business-flow testing once environment-specific grants, branch accounts/months, plans, salary/coach settings and browser routing are set. Classes pay, legacy 410 routes, historical subscription/payment import, and live browser/production behavior remain outside what can be claimed as working from this static audit.
