# V1 source readiness and operational prerequisites

**Source-contract result:** the original master V1 baseline exposes 227 controller operations, including all 36 Coaching operations, Owner access administration, Monthly Finance/Payroll, Shift override and branch-period reports, final Quick Cancel/Refund rules, optional InstaPay references, and five Planned Periodic Expense routes. The optional Excel Bulk Import addendum adds four actions on `Excel_import_export`, giving 231 controller operations. Runtime OpenAPI matches those routes. The baseline V1 source contract remains stable; Excel import requires its new migration before integration.

**Development schema:** after explicit Owner approval, `20261016114618_AddPlannedPeriodicExpenseDescriptionAndDueDate` was applied only to `localhost:5432/campions_gym`. Development now has **30 applied migrations, zero pending and 112 public tables**. The two nullable `MaintenancePlanRevisions` columns match the EF model; all 111 other table row counts match their pre-migration baseline. A timestamped custom-format backup was verified before application. Production state was not inspected and is not implied by Development.

**Excel import activation:** `20261016201337_AddExcelImportSessions` is prepared but **not applied to Development or Production**. Thus the prior 30-applied/zero-pending statement describes the V1 baseline before this new feature migration. Applying it requires separate approval. The new endpoints also require the same effective manual-create grants and open Shift rules, not a new broad import grant. See [Excel Bulk Import](EXCEL_BULK_IMPORT.md).

**Permissions and configuration:** a capability's presence in the catalog is not a role grant. A read-only query of this local Development database found `Shifts.CloseOthers` already granted to Owner and BranchManager, and `Payments.Refund` to Owner; those facts do not establish any particular user's effective access because Deny, activity and branch scope still apply. The following active V1 capabilities had **no role grants and no direct overrides** locally: `Classes.RegisterAttendance`, `CoachEarnings.ManageTargets`, `CoachEarnings.Pay`, `CoachEarnings.Recognize`, `CoachEarnings.View`, `FinancialMonths.Close`, `FinancialMonths.Export`, `FinancialMonths.Manage`, `FinancialMonths.Reopen`, `FinancialMonths.View`, `FinancialMonths.ViewConsolidated`, `Maintenance.Manage`, `Maintenance.View`, `Payroll.RecordPayment`, `Private.RegisterSession`, `Private.SettleExpiry`, `Private.Transfer`, `Salaries.Manage`, `Salaries.View`, `Sales.QuickCancel`, `Vault.View`, `Installments.Manage`, and `Offers.Manage`. An authorized Owner must choose intended role/account grants through `/api/access-administration`; this handoff does not assign them or assume every capability belongs to every staff role. `Vault.View` is required with `Shifts.View` for pre-closure transaction review. Explicit branches, assignments, financial accounts/drawers, salary settings, Sales/Coach targets and active financial periods are environment configuration, not frontend defaults.

**Infrastructure:** no CORS policy is currently registered; a separate-origin React client requires a proxy or separately approved backend CORS setup. API URL, certificates, Identity accounts, secrets and Production migrations/grants remain target-environment concerns. Backend startup does not auto-apply migrations or seed.

**Intentionally unavailable:** Classes compensation has no Owner-approved formula or rate. Monthly Closing/Payroll employee payment records do not prove source account movement; no automatic funding ledger row is created. Planned periodic expenses are forecasts, not reserve balances or automatic expenses. Four legacy Operations writes return 410. There is no refresh/logout/password-reset API or general City CRUD. Avoid inventing these in React.

**Historical contract limitation:** raw runtime OpenAPI omits many `IActionResult` success and authorization metadata; [integration supplement](openapi.integration.json) derives these from compiled source. Service-level Owner, branch, Shift, cash, and state guards remain in feature docs and can return errors beyond route annotations. Complete realistic flow testing should follow authorized migration/grant/setup activation.
