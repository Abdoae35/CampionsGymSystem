# Authentication, authorization and branch context

`POST /api/auth/login` takes `{userNameOrEmail,password}` and returns an access token, expiry and user identity. `GET /api/auth/me` returns the currently re-evaluated roles, effective permissions, linked employee and current branch; use it to bootstrap frontend access. Send `Authorization: Bearer <token>`. The server checks account activity/lock and employment state on protected requests. There is no refresh, server logout, self-registration or password-reset API. Clear local auth state on sign-out or 401; do not assume a 403 requires a new login.

The authoritative `PermissionService` unions active role grants and direct Allow overrides, then removes direct Deny overrides. **Deny wins.** Multiple Identity roles may belong to one account, including Manager plus Sales. Neither role labels nor frontend flags override server policy, current Owner membership, employee status, branch/actor scope or service rules. `/me.permissions` controls UI affordances; a mutation can still fail after state changes.

[Owner-only Access Administration](api/AccessAdministration.md) is implemented under `/api/access-administration`: read permission catalog, roles, users, effective explanations and audit history; PUT existing role membership, role grant and user Allow/Deny/Clear. Each action requires authenticated **current Owner membership** plus its `Roles.*` or `Users.*` capability. A Manager with those capabilities alone is forbidden. Changes are audited, serialized and immediately re-evaluated. Last usable Owner and self-lockout protection also applies to [employee lifecycle](api/Employees.md); these endpoints do not create new Owners or roles. Do not build client-side permission administration from role labels alone.

Employee branch context comes from active dated assignments and BusinessDate; ordinary staff act within their current permitted branch. An explicit route/query/body `branchId` is still scope checked. `Branches.AccessAll` permits authorized global operations only in combination with the action capability and any Owner/actor rule. No `X-Branch-Id` header or general branch-switch endpoint exists. Sales commercial owner is separate from the authenticated cashier: collecting a payment does not confer commission ownership. A Manager may also be a personal Sales owner on the same employee account.

Check the exact ANDed controller policies in the [catalog](API_ENDPOINT_CATALOG.md) and the [effective capability catalog API](api/AccessAdministration.md). Route policy presence does not prove an operational role grant. Owner-only maintenance writes, administrative refunds, payroll payments and coach settlements carry additional service-level membership checks. Branch Managers may close/reopen months and close another employee's Shift only with the appropriate effective capability and branch scope. They cannot administer access.

No backend CORS policy is registered in `Program.cs`; a separate-origin React app needs an approved backend CORS change or a same-origin development proxy. Never put JWT signing keys, database credentials or Owner passwords into frontend environment variables.
