## Startup and operational readiness

Login → `/api/auth/me` → show permissions/current branch → permitted `/api/branches` choices for global users → `/api/shifts/current`. A missing Employee/current branch is a setup state, not an empty valid operational context. Global selection is passed only in fields defined by the selected endpoint. Opening own Shift (`POST /api/shifts`) requires a configured shared drawer and actual physical opening count. Registration, new Sale, subsequent collection, cancellation/refund and operational payout require **this actor's own** open shift; another employee's Shift does not satisfy it. Report/configuration/auth reads need no shift.

## Members, Sales ownership and CRM

Search `/api/members` using actual supported filters; details `/api/members/{id}`. `POST /api/members` registers a profile only, not a membership/payment. `creationType` is explicit: NormalSales resolves the active eligible actor; ManagementCreated needs Members.AssignSales plus selected eligible Sales employee; FreelanceHouse needs an eligible Freelance plan/capability and no owner. Cross-branch registration requires capability and destination rules. ClientCode is allocated by backend within registration branch; MemberCode is global. Never send codes, verification flags, account links or arbitrary ownership fields through profile update.

`PUT /api/members/{id}` edits profile; primary phone changes also require Members.ChangePrimaryPhone. Shared branch-configured calling-code normalization protects duplicate identities. If an existing Lead uses that phone, use CRM lookup/conversion. `/sales-assignment`, `/sales-history`, `/assign-sales`, `/return-to-house` retain ownership history. Existing ownership persists across employee transfer; non-active employment returns Members to House.

Lead flow: `/api/leads/lookup?branchId=...&phone=...` → existing duplicate result or POST intake. Phone-only prospect is supported; complete name is required on conversion. Intake result discriminants include Created/AlreadyMember/AlreadyLead/Invalid; inaccessible private details/IDs can be withheld. Bulk is JSON rows (1..100), not Excel upload, with per-row results. `/api/leads/my` is actor-owned, not a client-selected employee bypass. Assignment validates eligible Sales in operational branch. Append interactions, schedule follow-up, mark Lost with reason, or reactivate with additional management capability. Converted is terminal; no direct status-to-Converted substitute.

`POST /api/leads/{id}/convert` preserves current eligible owner, uses destination branch's ClientCode, and atomically closes Lead assignment. Operator may convert another owner's Lead when authorized without accessing private details. Explicit Freelance conversion is the House exception. `/api/crm/my-follow-ups` combines owned tasks/scheduled Leads; House queue is scoped management work. Explicit open/complete/assign endpoints exist. Automatic expiry/inactivity generation and sending notifications do not.

## Product choice, purchase, renewal and entitlement

Read scoped plans, dynamic categories and benefits; never infer plan eligibility solely from `customerPurchasable`. Employee plans are internal opt-in. Branch owns administration; City defines access. Normal/Freelance template price can be zero but the paid Sales path requires positive payable price. Freelance eligibility preserves existing Sales/House ownership and sells only the fixed gym fee.

Select Member, plan, activation and permitted Offer → `/api/offers` eligible list → `/api/offers/quote` backend pricing → select accounts `/api/financial-accounts` → `POST /api/sales`. Never submit trusted final price, Sales employee, commission or session balances. Sales snapshots price/Offer/access/benefits, so later template edits do not change bought terms. Offer General and MemberOnly are explicit; MemberOnly requires active grant; plan audience eligibility remains authoritative.

PurchaseMode numeric: FullPayment=0, Reservation=1, Installment=2, StandaloneSingleSession=3. ActivationMode numeric: Now=0, FirstCheckIn=1, SpecificDate=2. FullPayment tenders exact final price. Reservation requires positive deposit; optional due date does not automatically cancel; no entitlement until fully collected. Additional payment through `/api/sales/{id}/payments` must match positive parts exactly. Installments additionally require Installments.Manage, 1..100 obligations summing to unpaid balance, and an explicit positive initial threshold or positive initial tender. Zero-money installment creation records no Payment/access. Later payment must explicitly allocate all its money to obligations; no overpayment/allocation.

Qualifying collection activates internally, atomically. No public subscription-purchase or renewal endpoint exists. FirstCheckIn can remain undated/ready until a valid actual entrance; blocked entrance must not start it. SpecificDate is future-only access; completion after chosen date starts at actual qualifying BusinessDate. Early compatible same-mode renewal appends time/active sessions immediately; expired unused sessions never carry. Mode/scope change schedules an unstarted successor; conflicting future grants fail rather than overlap. Inclusive period end = start + duration - 1. Sold city/access snapshot is authoritative.

Read `/api/members/{memberId}/subscriptions/current`, history and details. Normal freeze uses allowance from immutable grants, needs original `expectedVersion` and operation identity, books non-overlapping dates and extends end once. Completion after inclusive freeze end is acknowledgment, not early unfreeze; no early-unfreeze/cancel route. Custom medical extension requires elevated permission/reason, does not consume normal allowance or block entrance. Official holidays require global + Extend, apply branch-specific policy without freeze/holiday double compensation; future declarations need explicit apply (no scheduler). Employee free entitlement is explicit existing Employee/Member/Employee-plan workflow; status closure and rehire preserve history.

## Check-in, trial and borrowing

Lookup `/api/check-ins/members`, then optional read-only `POST /api/check-ins/evaluate`; actual `POST /api/check-ins` re-evaluates under locks. Exactly one MemberId/MemberCode; Scanner=0 requires MemberCode, Manual=1 accepts identity, Coach=2 is rejected for gym entrance. MemberCode text can come from scanner/QR; no hardware API/QR generation exists. **HTTP 200 may be a business denial**: inspect `decision.allowed` and `reasonCode`, not only status. Denials create no entry. FirstCheckIn activation, session consumption and entrance commit together.

Each actual SessionBased entry consumes one; two distinct same-day entries consume two. Unlimited keeps null sessions. No one-per-day shortcut. Date expiration blocks even with unused sessions. City mismatch/freeze/closure/inactive employee/overdue installment/ambiguous entitlement deny. An obligation is overdue when DueDate < BusinessDate; paying all overdue amounts restores access without extra days.

Expired eligible customer cycle permits at most two BorrowedGym entries with **explicit confirmBorrow=true**. Exhausted but unexpired, Employee, cancelled/frozen and standalone visits do not become borrow cycles. A true renewal settles all outstanding debt: SessionBased 12 less debt 2 yields 10; insufficient new sessions rejects all; Unlimited settles without quantity deduction. Standalone paid visit does not settle/reset debt. Normal cancellation can append debt-settlement reversal; history is retained. Trials redeem an existing invitation at its branch with matching canonical phone; no issuance route, auto-member creation or paid session deduction. GUEST benefit use is consumed once when applicable. Trial result can also be HTTP 200 denied.

## Cash, cancellations and operational finance

Money is backend decimal(18,2). One split Cash+InstaPay payment is one collection with two parts. Part amounts sum exactly. Account method/branch determine posting; no frontend-provided balance overrides. `SaleDetails` and dedicated paginated payments/refunds/installments are authoritative; embedded detail histories are bounded to first 100.

Normal refund `/api/sales/{id}/refunds` is management's chosen zero/partial/full cancellation amount, capped by real unrefunded collections. Zero cancellation has empty parts; positive parts specify exact outbound accounts. No automatic per-day/session formula. Cancellation preserves delivered entries and immutable grants; reverses unused grant contribution only once. Retained funds remain CancellationFee without another ledger credit. Finalized commission source protection can block a positive refund atomically with 400.

Quick Cancel needs independent Sales.QuickCancel, exact 24 actual hours and unused grant. Material entrance/benefit/freeze/extension/debt settlement blocks it; old configurable refund-window metadata does not change this hardcoded 24-hour rule. It returns money to original accounts, including inactive historical sources. No delete/rewrite of sale/payment history.

Shared physical drawer: one mapped Cash account per branch, overlapping employee Shifts, manual own closure. `/api/vault/setup` requires global authorization; counts observe real money, never invent revenue. Book balance = opening + credits - debits. Physical position = latest count + subsequent ordered movements. Count discrepancy is a branch observation; no payroll deduction/fake expense. Cash payout cannot exceed tracked physical cash. InstaPay is separate; negative book position is not a claimed bank overdraft check.

`POST /api/expenses` records actual paid expense and one debit; dynamic categories have separate global administration. `/returns` requires actual returned funds=true, positive amount within paid-less-returns, original account and reason; appends credit/history. Advance is separate from expense/payroll, with actual receiving Employee/recording actor/account; no repayment/settlement API. Withdrawal needs Vault.Withdraw AND Branches.AccessAll AND own shift, no default manager grant.

Close `/api/shifts/{id}/close` with original version/count/reason; only opener, final closure. Reconcile using historical closing snapshot and current branch drawer separately. Explicit `/api/business-days` close/open can leave Shifts open across midnight/day turnover; closing a Shift does not close BusinessDay. No auto/forced close, discrepancy-resolution or routine external Cash-In workflow.

## Independent Sales commissions

Configure `/api/commissions/rules` explicitly before first period: branch fallback (`employeeId:null`) and employee overrides, independent New/Renewal target/below/reached rates. No defaults seeded. Rule revisions are future-effective at next period boundary. `/periods` uses explicit contiguous inclusive BusinessDates and one Open period per branch. Money can be recorded before setup but dated evidence remains; never fabricate legacy dates/period links.

Progress `/periods/{id}`, employee statements, `/sources`, `/refund-allocations` expose actual retained collections and estimate/finalized status. First-ever gym purchase includes prior pending/cancelled history across branches; later purchases are Renewal. Original commercial employee is snapshotted, not cashier/current owner; later receipts after ended employment become House. Actual local PaidAt employment date is distinct from effective period BusinessDate. Freelance/standalone excluded. Parts/installments are not additional revenue.

Target attainment changes rate on all eligible category money independently; aggregate once, round each category AwayFromZero to 2 decimals, then sum. Frontend may format progress but must use returned commission values. Refund allocates newest actual payments first; if any allocated source is finalized, the whole refund rejects without changing money/entitlement. Finalize needs global+ClosePeriod, original expectedVersion, configured categories, and effective BusinessDate later than EndDate. Frozen evidence/rates are read thereafter. It is not payout, payroll or monthly close.

## UX and retry recommendations

**RECOMMENDATIONS**: use loading/empty/denied/validation/conflict states separately; disable duplicate submit while pending; keep OperationId **and exact original payload** after network uncertainty; do not generate a new identity merely to retry. New real action needs new identity. Changed-payload operation reuse is a 400 business rule in several services, not uniformly 409. Profiles/catalog edits lack general idempotency keys; confirm outcome before blind retry. No ETag/If-Match contract exists. Stale expectedVersion → refresh authoritative data, show conflict and request deliberate resubmission.

Guard cancellation/refund, Shift count/close, withdrawal, actual expense return and finalization with specific summaries/confirmation. Preserve zero/null meaning; null sessions are Unlimited/unknown, never zero. Input decimal strings using decimal-safe validation; display locale formatting only. Keep backend dates as YYYY-MM-DD and UTC instants separately. Invalidate related member/entitlement/access/Sale/financial/commission queries after successful operations; clear protected cache when user/context changes. Avoid optimistic money/session deduction. Never turn unknown legacy facts into invented state.
