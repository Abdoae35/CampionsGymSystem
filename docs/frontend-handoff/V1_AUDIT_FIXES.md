# Six completed backend audit fixes: frontend effects

All six changes are present in current `master` at `e3b8cc3`. This page identifies the final behavior exposed to React; it does not imply any Production migration or role grant. Exact routes and DTOs are in the [operation catalog](API_ENDPOINT_CATALOG.md) and [OpenAPI supplement](openapi.integration.json).

| Fix | Current behavior and integration effect | Source evidence |
|---|---|---|
| 1. Owner lifecycle protection | Employee status/other lifecycle edits cannot disable a protected Owner, the last usable Owner or the acting Owner through self-lockout. Treat denial as authoritative; do not hide protection behind UI role logic. | `CampionsSystem.BLL/Employees/EmployeeManagementService.cs` `ChangeStatusAsync`; `CampionsSystem.BLL/Authentication/OwnerAccountProtection.cs` |
| 2. Shift integrity and shared drawer | Employees open their own Shift manually before reception financial work. Authorized in-scope Manager/Owner can close another employee's Shift using `POST /api/shifts/{id}/close-override`. No count records `Unverified` and null discrepancy. `GET /api/shifts/{id}/summary`, `/transactions` and `/branch-transactions` separate own activity from all branch-period movements and expected Cash/InstaPay balances. Owner paid expenses can be recorded without an Owner Shift and retain actual operator identity. | `CampionsSystem.BLL/Shifts/ShiftService.cs`, `ShiftReportService.cs`; `CampionsSystem.API/Controllers/ShiftsController.cs` |
| 3. Quick Cancel and refunds | Reception Quick Cancel is allowed through 24 actual hours inclusive with explicit zero/partial/full amount; Gym, Private and Classes usage does not impose an automatic deduction. Later cancellation uses elevated `POST /api/sales/{id}/refunds` by authorized Manager/Owner. Net-collected cap, branch, Shift and finalized-period safeguards still apply. | `CampionsSystem.BLL/Sales/SalesService.QuickCancel.cs`, `SalesService.Refunds.cs`; `CampionsSystem.API/Controllers/SalesController.cs` |
| 4. Payroll recognition retries | `POST /api/payroll/commission-recognitions` serializes the same `operationId` across branches. Exact committed retry returns the recorded result; changed period/actor rejects; a rolled-back attempt may safely retry. React must retain the same UUID/body/actor on uncertain network response. | `CampionsSystem.BLL/MonthlyFinance/PayrollService.cs` `RecognizeCommissionPeriodAsync`; filtered unique audit marker migration |
| 5. InstaPay references | `providerReference` remains optional on payment/refund parts. When stored, monthly transaction evidence and XLSX export include the reference for its actual account ledger row; null/empty produces a blank cell. A split payment is not counted twice. A reference is not automatic bank verification. | `CampionsSystem.BLL/Sales/SalesContracts.cs`; `CampionsSystem.BLL/MonthlyFinance/MonthlyReportBuilder.Transactions.cs` |
| 6. Historical Monthly Closing scale | A month's detailed transactions and obligations belong to that month. Historical data supplies opening/outstanding balances through bounded aggregates; old detail is not copied into the current month's financial-transaction sheet. Frozen earlier revisions remain intact. The genuine 50,000-row current-period detail bound remains. | `CampionsSystem.BLL/MonthlyFinance/MonthlyReportBuilder.cs` and related payroll/coach aggregate queries |

The four legacy Operations writes returning 410, Classes compensation remaining `NotConfigured`, and informational maintenance forecasts remain distinct from these fixes. See [workflow guide](V1_WORKFLOWS.md) and [activation prerequisites](OPEN_QUESTIONS_AND_GAPS.md).
